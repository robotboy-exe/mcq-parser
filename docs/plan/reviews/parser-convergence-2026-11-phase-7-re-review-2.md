## New findings and finite closure contracts

### BLOCK-24 — Key-only Load confirms Active for the batch it just corrected

**Rule and severity:** `docs/SPEC.md:723–728` says “metadata, key, or mode changes clear the confirmation but keep the active choice”; the existing-batch key behavior is also explicit in `docs/DECISIONS.md:641–650` (D-51). The approved PC07 fix-2 `D2` (`pc-07-stimulus-first.md:180`) says Start “remains disabled until the user explicitly confirms Active or switches to Draft and confirms Draft.” This is the ordinary **Show paste box → paste only the key → Load** workflow, with the same valid batch still pending. The real POST violates that confirmation requirement and publishes a row; this is a directly unmet requirement, even though the unconditional Load reset predates fix 2.

**Reproduction:** On authenticated staging Add (subject 10/category 4/year 2083), load two complete A–D items with key `1. A` / `2. C`. Confirm Draft, Start, hold Q1's POST, activate the same artifact once, release, and wait for real settlement. SQLite `#119` is inactive; at `i=1` the panel shows Active, confirmation unchecked, Start disabled, and Q2/C. Use **Show paste box** and Load only `Answer Key\n1. A\n2. D`; let the automatic dry run finish. The exact batch ID and `i=1` are unchanged, Q2 now ticks D, and the Q1 saved list is unchanged. But confirmation is now **checked** and Start is enabled with no check by the reviewer. Click it once: the only Q2 POST sends `correct_option=3`, `autosave=1`, `is_active=1`. SQLite `#120` is active, answer D; the log is `[[1,119,"draft",true],[2,120,"active",false]]`. On an ordinary confirmed Draft batch before any save (year 2091), key-only `1. D` / `2. C` also changes the same queue from Draft to Active and leaves confirmation checked and Start enabled; no save attempted in that control. Loading actual replacement questions creates a **new** batch with both defaults checked, as required.

**Cause:** `src/ui/ui.js:602–609` sets the mode and confirmation defaults. `:867–881` calls it before testing whether the paste is key-only; `:882–903` applies the key and renders the retained queue without clearing confirmation. `:549–553` therefore enables Start and `:810–819,841` selects Active. `src/bookmarklets/stimulus/save-flight.js:135–139` serializes that selection. The genuine mixed-mode log is not a stale paint or server mismatch.

**Closure/evidence:** (1) For the exact held-Q1/reinject/settle/key-only sequence, the key correction must still update Q2 to D in the same batch at `i=1`, but keep Active selected and confirmation unchecked and issue **zero** Q2 POSTs on an unconfirmed Start attempt. Explicitly select and confirm Draft; a subsequent Start must POST Q2/D once without `is_active` and persist it inactive under book 2. (2) For the ordinary already-confirmed Draft control, key-only correction keeps Draft, clears confirmation and disables Start until a new tick. (3) A new questions paste still gets a new batch ID and the approved checked defaults. Require a failing-first regression against the generated artifact and disposable browser replay with mode/confirmation, multipart and queried row evidence; retain the original `BLOCK-23` mode controls. **Non-goals:** new-batch opt-in policy, parser/key grammar, persisting mode across reloads, changes to storage shapes or PHP, empty/invalid pastes, or comparator retirement.

### BLOCK-25 — Same-page activation after settlement silently re-arms Active confirmation

**Rule and severity:** In the same approved `D2` (`pc-07-stimulus-first.md:180`), Start “remains disabled until the user explicitly confirms Active or switches to Draft and confirms Draft.” `docs/SPEC.md:717–729` identifies a new paste as the checked-default boundary. Here there is no paste, key edit, navigation, or new batch: the user repeats activation on the same Add form. That replaces the panel and bypasses the explicit post-adoption confirmation gate; the resulting Active row is independently reproduced. This trigger is separate from the key-only Load handler and from the obsolete-generation paint fixed in `BLOCK-23`.

**Reproduction:** On authenticated staging Add (subject 10/category 4/year 2094), use two complete A–D questions keyed `1. A` / `2. C`. Confirm Draft, Start, hold Q1, activate the artifact, release Q1, and wait until settlement. At generation 1 the form has `i=1`, Q2/C, `1/2`, one verified Draft entry for `#144`, no in-flight save or marker, and visibly Active selected, confirmation **unchecked**, Start **disabled**. Activate the same artifact a second time, now **after** settlement. Generation 2 retains the batch ID, index, answer key, Q2 radio and log and issues no POST during activation, but it checks the Active confirmation and enables Start. With no intervening mode or confirmation click, Start posts Q2/C once with `autosave=1` and `is_active=1`. SQLite `#145` is active; the final log records Q1 Draft and Q2 Active. The separate two-activations-while-GET-held control before settlement produced no bypass.

**Cause:** `src/ui/ui.js:157–160` initializes a fresh instance with Active and both confirmations true. Cleanup increments the generation (`:1166–1176`); the new render reads the same `ocrQueue` and saved log (`:120–135,1178–1180`). Clearing in `:1181–1214` is limited to an observation of an in-flight save. Once `save-flight.js:323–328` has cleared `owner.inFlight`, `attachObserver` returns `false` (`:332–345`). The idle activation therefore leaves the fresh checked defaults on the same, still-unconfirmed batch.

**Closure/evidence:** On the exact same-form held-Q1 → activate → settle → activate-again sequence, keep `i=1`, Q2/C and the single verified Q1 log, with no new POST on activation and none on an unconfirmed Start. The displayed mode and unchecked confirmation must agree with the blocked Start even though the flight and marker are gone. Explicitly select and confirm Draft; one Start must send only Q2/C without `is_active` and persist it inactive under book 2. Keep the original one-activation `BLOCK-23` and the two-activations-while-verifying control. Require failing-first built-artifact regression and a real held-POST staging replay with generation/queue, widget, multipart and row evidence. **Non-goals:** browser reloads, another tab or product taking ownership, storing a draft preference, adding persistent keys, changing new-paste defaults, or auto-resuming a run.
